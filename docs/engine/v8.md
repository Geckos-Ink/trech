# V8 JavaScript backend

[Documentation home](../README.md) · [Engine index](README.md) · [Build](../build.md) · [CLI and live lab](cli.md)

TRECH scenarios are JavaScript. By default TRECH evaluates them, and runs their hooks, in
QuickJS, a small interpreter. A TRECH binary built with `-DTRECH_ENABLE_V8=ON` can run the same
scenarios on **V8**, Google's JavaScript engine, which compiles hot code to machine code. Use it
when hooks do real computation: a JavaScript particle model, a per-event field update, a hook
that runs on every step. On those scenarios V8 is several times faster, and the results are the
same bytes as on QuickJS.

## Build with V8

CMake never builds or downloads V8. Give it one that is already built, in one of three ways:

| Source | When | Configure with |
| --- | --- | --- |
| Homebrew (macOS) | Quickest: `brew install v8` downloads a prebuilt V8 (15.9.128.11 when this was written). | `-DTRECH_ENABLE_V8=ON` (Homebrew's prefix is found automatically) |
| From source | Any platform, a pinned revision, a debug V8, or a static binary: [`scripts/build_v8.sh`](../../scripts/build_v8.sh) builds the `thirds/v8` submodule as `libv8_monolith.a`. It downloads depot_tools and V8's dependencies (several GB) and compiles for a long time. | `-DTRECH_ENABLE_V8=ON -DTRECH_V8_BUILD_DIR=<out dir>` |
| Other install | A distribution package or your own install with `include/v8.h` and `lib/libv8*`. | `-DTRECH_ENABLE_V8=ON -DTRECH_V8_ROOT=<prefix>` |

```sh
brew install v8
cmake -S . -B build/v8 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH=/path/to/geant4-install -DTRECH_ENABLE_V8=ON
cmake --build build/v8
./build/v8/trech inspect examples/scenarios/hello_world/hello_world.js --js-engine v8
```

The from-source route, if no package fits:

```sh
scripts/build_v8.sh                       # thirds/v8/out.gn/trech/obj/libv8_monolith.a
cmake -S . -B build/v8 -DTRECH_ENABLE_V8=ON -DTRECH_V8_BUILD_DIR=$PWD/thirds/v8/out.gn/trech
```

`scripts/build_v8.sh --help` lists its options (`--out`, `--jobs`, `--debug`, `--gn-args`). It
builds without pointer compression, sandbox or ICU, so the embedder needs no extra definitions.

**ABI definitions.** Code that embeds V8 must be compiled with the same pointer-compression and
sandbox settings as the V8 library, or V8 aborts at start-up. `TRECH_V8_DEFINITIONS=AUTO` (the
default) finds them at configure time: it builds and runs a tiny probe
([`cmake/v8_abi_probe.cpp`](../../cmake/v8_abi_probe.cpp)) for each known combination and keeps
the first that runs. Homebrew's V8 needs `V8_COMPRESS_POINTERS;V8_31BIT_SMIS_ON_64BIT_ARCH`; the
configure log prints the result. When cross-compiling, set the list yourself.

QuickJS is always built, so a V8 binary can run both engines.

## Choose the engine

The first match wins:

1. `--js-engine quickjs|v8` on `trech run`, `inspect` or `lab`.
2. The `TRECH_JS_ENGINE` environment variable (`quickjs` or `v8`). Studio and scripts that start
   `trech` pass it through.
3. The build default, `TRECH_DEFAULT_JS_ENGINE` (`quickjs` unless configured with
   `-DTRECH_DEFAULT_JS_ENGINE=v8`).

Asking for V8 in a binary built without it stops with an error naming `TRECH_ENABLE_V8`.
A run on V8 records `"js_engine": "v8 15.9.128.11"` in
[`trech_provenance.jsonl`](output_schema.md#trech_provenancejsonl), and a V8 live lab records it in
each [`lab_script`](output_schema.md#lab-script-identity). QuickJS runs omit the field, so their
records are unchanged.

In C++, `trech::JsRuntime(trech::JsEngine::V8)` selects the engine for one runtime, and
`JsRuntime::setDefaultEngine` for every later default-constructed one.

## What stays identical, and why

Both engines run the **same host code**: TRECH_INCLUDE, TRECH_READ_JSON, TRECH_VALUE,
TRECH_PUBCHEM, the hook `ctx`, `ctx.rng`, `ctx.emit`, overrides, and every inference API
(`ctx.predict`, `ctx.cascade`, `ctx.evolve`, `ctx.react`, `ctx.interact`, `ctx.lift`,
`ctx.learnDomains`, `ctx.evolveField`, …). They also share **the same Math**: V8's `Math.exp`,
`Math.sin`, `Math.pow`, `Math.hypot` and the other transcendental functions are replaced by
TRECH's deterministic `trech_dmath` C functions, which QuickJS uses too. Everything else that
reaches a result, such as `+`, `*`, `sqrt`, number formatting and JSON, is defined to the bit
by the JavaScript standard and IEEE-754, so both engines agree on it.

Verified on macOS arm64 with Homebrew V8 15.9.128.11 (2026-11-21):

- `trech inspect` of all 71 repository scenarios: byte-identical output on both engines
  (68 succeed; 3 stop on both with the same PubChem cache-miss message).
- Whole `trech run`s compared file by file with
  [`scripts/js_engine_run_parity.py`](../../scripts/js_engine_run_parity.py): `hello_world`,
  `hooks_track_ledger`, `cascade_multiscale_demo`, `surrogate_generic_demo`, `h2o_bulk_water`,
  `briggs_rauscher_oscillator` and `lava_lamp` (244 hook emits, including the engine's
  field-evolution arbitration) are identical. `config_hook_dispatch` differs, but so do two
  QuickJS runs of it: it runs multi-threaded, and emit order across Geant4 workers is not yet
  fixed (a queued runtime item), so the tool reports it as not replayable rather than as an
  engine difference.
- The JavaScript test suites (`trech_js_runtime`, `trech_lab_script_host`,
  `trech_deterministic_math`, `trech_scenario_bundle`, `trech_scenario_helpers`,
  `trech_geometry_generators`) pass on V8 as their `_v8` CTest twins, and
  `trech_js_engine_parity` compares both engines directly: configs, typed values, RNG draws,
  emits, overrides, Math results, errors, engine swaps and threaded dispatch.

```sh
python3 scripts/js_engine_run_parity.py --trech build/v8/trech --timing
```

The tool pins `TRECH_COMPUTE_BUDGET` for both engines. Without a pin, learner capacities come
from a timing probe of the machine, so even two QuickJS runs of a learning scenario such as the
lava lamp can differ when the machine is busy. It also runs QuickJS twice when a difference
appears, to tell an engine difference from a scenario that does not replay at all.

## What differs

- **The `**` operator is refused.** V8 computes `a ** b` with its own pow and JavaScript cannot
  replace an operator, so the result could differ from QuickJS in the last bit. The V8 backend
  therefore refuses any script containing `**` or `**=`, with its location:
  `…/scenario.js:12:9: the ** operator is not supported by TRECH's V8 backend … Write Math.pow(a, b)`.
  Strings passed to `eval` or `new Function` are checked the same way and refused with an
  `EvalError`. `Math.pow` gives the same bits in both engines (QuickJS computes `**` with
  it). `python3 scripts/check_js_pow_operator.py <paths>` lists every use; the repository's
  scripts have none (CTest `trech_js_pow_operator`).
- **Stack traces** use QuickJS's `    at name (file:line:column)` layout, but V8 names functions
  more fully (`TRECH_CHECKS.glass_from_sand.observeFrame`), reports some columns differently and
  does not list native frames such as `TRECH_PUBCHEM (native)`. Error messages are the same.
- **Host functions are shared objects.** On V8, `ctx.emit` and the other `ctx` functions are the
  same function objects in every dispatch (QuickJS makes new ones each time). Only a script that
  compares or decorates them could notice.
- **Promise callbacks never run**, as in QuickJS: TRECH runs no job queue on either engine.

## Measured speed

Wall time of whole `trech run`s on one machine (macOS arm64, Release build, Homebrew V8
15.9.128.11, 2026-11-21; `scripts/js_engine_run_parity.py --timing`). Geant4 transport is the
same on both; the difference is the JavaScript:

| Scenario | What the hooks do | QuickJS | V8 |
| --- | --- | ---: | ---: |
| `h2o_bulk_water` | water molecular dynamics in JavaScript | 70.2 s | 6.1 s |
| `briggs_rauscher_oscillator` | reaction kinetics per event | 4.3 s | 1.7 s |
| `lava_lamp` | engine field evolution (C++) plus JavaScript observers | 102 s | 77 s |
| `hello_world`, `hooks_track_ledger`, `cascade_multiscale_demo` | little JavaScript | 0.9–1.4 s | 0.9–1.1 s |

The gain is largest where time is spent in JavaScript loops; it is small where Geant4 or the
engine's C++ inference dominates. V8 creates a runtime in a few milliseconds more than QuickJS,
which does not matter for a run but is visible for very short `inspect` calls.

## Measure your hooks

`trech-js-bench` times evaluation and hook dispatch on each engine, without Geant4:

```sh
./build/v8/trech-js-bench                      # built-in workload: an empty hook and a 96-particle LJ step
./build/v8/trech-js-bench --dispatches 500 examples/lab/live_hook_tuning.js --hook onEventEnd
```

It prints one JSON line per engine with `create_ms`, `evaluate_ms` and `us_per_dispatch` for
each hook. On the machine above, the built-in workload gave (three runs, 2000 dispatches each):

| | QuickJS | V8 |
| --- | ---: | ---: |
| create a runtime | 1.5 ms | 3.6–4.2 ms |
| evaluate the workload script | 2.5–6.4 ms | 0.5–0.6 ms |
| empty hook (`onEventStart`): fixed cost of `ctx` and the call | 4.7 µs | 6.3 µs |
| 96-particle Lennard-Jones step (`onStep`) | 745 µs | 61–94 µs |

So V8 costs about 1.5 µs more per dispatch for a hook that does nothing, and is 8–12 times
faster once the hook computes. The empty hook shows the fixed cost of building `ctx` and calling into JavaScript;
the particle step shows compiled JavaScript arithmetic. A scenario's hooks get a synthetic
context, so a hook that needs Geant4 material probes may throw; pick a hook that does not.

Studio starts `trech` with its own environment, so launching Studio with `TRECH_JS_ENGINE=v8`
runs its live lab and runs on V8 (Studio has no engine selector yet).

Use it to decide whether a live lab should run on V8: if the hooks take a large share of a
batch on QuickJS, V8 frees that time for more events per batch or a finer model.

## How it works

TRECH's host is one C++ file, [`src/js/JsRuntime.cpp`](../../src/js/JsRuntime.cpp), written against
the QuickJS C API. The default build compiles it with QuickJS.
[`src/js/JsRuntimeV8.cpp`](../../src/js/JsRuntimeV8.cpp) compiles the same file a second time against
[`src/js/V8QuickJsApi.hpp`](../../src/js/V8QuickJsApi.hpp), a V8 implementation of the 62 QuickJS
functions the host uses. Each build lives in its own namespace;
[`trech::JsRuntime`](../../include/trech/js/JsRuntime.hpp) is a facade that creates the chosen one.
So there is no second copy of the host to keep in step: a new `ctx` API works on both engines
as soon as it compiles.

The layer follows QuickJS where results depend on it: arguments are padded with `undefined` to
a function's declared length, `JS_ToInt64` uses QuickJS's exact conversion (the `ctx.rng` stream
depends on it), exceptions raised inside host functions reach the script unchanged, and `Math`
is `trech_dmath` with QuickJS's argument handling (`Math.pow(1, Infinity)` is `NaN`,
`Math.hypot` folds pairwise). Optimized V8 code calls the Math functions directly through V8's
fast API. Every entry point takes a `v8::Locker`, so Geant4 worker threads can dispatch hooks
one at a time, as with QuickJS.

## Node.js checks (without an embedded V8)

Before the embedded backend existed, two tools compared QuickJS with an installed Node.js
(whose engine is also V8). They remain useful on machines without a V8 build:

- [`scripts/js_engine_differential.py`](../../scripts/js_engine_differential.py) runs one
  scenario's top-level JavaScript in `trech inspect` and in a minimal Node host and compares
  Math, RNG and a water MD trajectory bit for bit. With `--dmath` it first installs
  [`js/trech_dmath_v8.js`](../../js/trech_dmath_v8.js), which puts `trech_dmath` (compiled to
  WebAssembly, [`js/trech_dmath_wasm_data.js`](../../js/trech_dmath_wasm_data.js)) into Node's
  `Math`. Recorded 2026-11-21 with Node 24.21.0 / V8 13.6.233.17: bit-identical (CTest
  `trech_js_engine_differential_dmath`). Without it, V8's own `pow`, `hypot` and fused
  multiply-add in `exp` differ from QuickJS by one ulp on some inputs.
- CTest `trech_dmath_wasm` checks the WebAssembly module against the C golden digests;
  regenerate it with `python3 scripts/build_dmath_wasm.py` (needs Emscripten).

The embedded backend links `trech_dmath` natively instead, which is faster than the
WebAssembly module. `trech-v8-probe` (`-DTRECH_ENABLE_V8_PROBE=ON`) still checks that a V8 build
links, runs and round-trips an in-process code cache.

The separate [atomic research tool](../research/atomic_stability.md) runs its numerical core on
an installed Node.js; it is unrelated to the simulation host.
